# BUG-012 — El seed comercial no crea cuentas autenticables

## Síntoma

Tras ejecutar `bdseed/seed_demo.sql` en producción, el contenido público parece
poblado pero no existe ninguna cuenta `@adoptiademo.com` en `auth.users`. El
login devuelve `400 invalid_credentials`. Producción conserva 13 cuentas del
seed de circuito y 100 del masivo.

## Causa y riesgos del script anterior

- El bloque Auth insertaba en `auth.users` pero no creaba `auth.identities`.
- `on conflict (id) do nothing` podía conservar silenciosamente credenciales
  antiguas.
- El resumen final contaba filas, pero no comprobaba contraseña, estado Auth ni
  la identidad canónica de email.
- La limpieza estaba repartida entre tres scripts, lo que facilitaba dejar
  seeds mezclados.

## Solución implementada

1. La única secuencia operativa admitida es `seed_todos_borrar.sql` seguido de
   `seed_demo.sql`. El limpiador es transaccional y está limitado a
   `@adoptiademo.com`, `@circuito.adoptia.es` y `@masivo.adoptia.es`.
2. El seed hace un preflight de los 19 UUID/emails e identidades canónicas antes
   de mutar Auth, y aborta si se intenta ejecutar aislado sobre restos de la
   demo. La convergencia garantizada corresponde a la secuencia completa.
3. Las 18 cuentas de protectora/adoptante reciben la contraseña demo local y
   un estado Auth normalizado. El perfil admin conserva sus datos de aplicación,
   pero queda bloqueado para login con un hash aleatorio no recuperable.
4. Las aserciones SQL finales verifican el mapeo exacto, el estado Auth, las 19
   identidades y perfiles, las 8 protectoras y los 40 animales.
5. El validador automatizado comprueba el contrato estructural mantenido de los
   dos SQL, incluida la exclusión del secreto demo de archivos rastreados.
6. El bloqueo del admin usa `timestamptz '9999-12-31 00:00:00+00'` en lugar de
   `'infinity'`. GoTrue no sabe escanear `'infinity'` en `banned_until`
   (`unsupported Scan ... into type *time.Time`) y respondía `500 Database error
   querying schema` en vez de rechazar la credencial; con la fecha finita
   devuelve `400 User is banned`.

## Verificación real ejecutada

Ejecutado el 2026-08-20 contra el stack local (`npx supabase start`, PostgreSQL
17 de Supabase) partiendo de `supabase db reset`:

- La secuencia `seed_todos_borrar.sql` + `seed_demo.sql` termina en `COMMIT` sin
  disparar ninguna aserción.
- El limpiador respetó el allowlist: borró las 13 cuentas `@circuito.adoptia.es`
  y dejó intactas las 6 cuentas locales ajenas a los tres dominios.
- Los recuentos de la consulta documentada dan `19 / 19 / 19 / 8 / 40`.
- Login real por API de Auth (`grant_type=password`):
  `protectoraaitana@adoptiademo.com` y `adoptantealcaraz@adoptiademo.com`
  devuelven `HTTP 200` con `access_token`; el admin devuelve `400 User is
  banned` y una contraseña incorrecta `400 Invalid login credentials`.
- Repetir la secuencia sobre una base ya sembrada converge a los mismos
  recuentos (idempotencia comprobada).

## Criterios de aceptación

- [x] El SQL de limpieza bloquea `auth.users`, revalida el allowlist al borrar y
  aborta si deja restos vinculados.
- [x] El SQL conserva y restaura los estados `O/R/A/D` de los triggers de
  usuario de `audit_log`.
- [x] El seed incorpora preflight, reinicio Auth completo, admin bloqueado y
  aserciones finales del mapeo y cardinalidades.
- [x] El validador estático y sus pruebas automatizadas cubren el contrato.
- [x] Ejecución real contra PostgreSQL de la secuencia cleanup + seed.
- [x] Confirmación real de los recuentos `19/19/19/8/40` tras esa ejecución.
- [x] Login real correcto para una protectora y un adoptante.
